Overview

Three ESP8266 NodeMCU boards on the same Wi-Fi network, each running its own local clock. The goal is to get them synchronized by exchanging timestamps over UDP and correcting for offset and drift in software. No external time source, no GPS. Just the boards talking to each other.

The idea came from a paper by Sivrikaya and Yener at RPI, "Time Synchronization in Sensor Networks" (IEEE Network, 2004). It was assigned reading in one of my courses. The paper surveys the problem from first principles: hardware clocks drift unpredictably, message delays add noise, and cheap devices can't afford the overhead of NTP or GPS. The approaches it covers, specifically TPSN and Tiny-Sync/Mini-Sync, give a clean framework for thinking about how to estimate offset and drift from timestamp exchanges alone.

This project is an independent implementation to see what those algorithms actually look like running on real hardware with real Wi-Fi latency.

Clock Model

CLK-001

Every hardware clock has two imperfections: drift and offset. Drift is the rate error, how fast or slow the oscillator runs relative to real time. Offset is the value difference at any given instant. The paper models each node's clock as a linear function of real time:

Ci(t) = ai · t + bi

ai is the clock drift (ideally 1.0 for a perfect clock) and bi is the offset from real time. Two clocks can be related to each other as:

C1(t) = a12 · C2(t) + b12

where a12 is the relative drift between the two and b12 is their relative offset. Synchronization means estimating these two values from timestamp exchanges and applying software corrections so each slave can convert its local time to match the master.

  • Correcting only offset is not enough. Clocks will drift apart again immediately.
  • Correcting both offset and drift keeps nodes synchronized over time without constant re-sync.
  • The linear model holds well as long as the sync interval is short relative to the drift rate.

Synchronization Method

SYN-001

The approach follows the two-way message exchange from TPSN. Node A sends a packet to node B with timestamp T1. B records its receive time T2 and replies with T3. A records T4 on receipt. From those four timestamps:

offset Δ = ( (T2 - T1) - (T4 - T3) ) / 2

one-way delay d = ( (T2 - T1) + (T4 - T3) ) / 2

The offset estimate assumes the propagation delay is symmetric. That's approximately true over a short-range Wi-Fi link but introduces error when the network is uneven. Repeating the exchange and averaging reduces noise from variable message delay.

  • Master initiates sync exchanges periodically
  • Slave estimates offset and applies correction to its local clock
  • Multiple rounds allow linear regression for drift estimation (Tiny-Sync approach)
  • Each (T0, Tb, Tr) triple constrains the possible drift and offset values

Two-Way Message Exchange

The core of the synchronization is four timestamps from a single round trip between master and slave:

TimestampRecorded byMeaning
T1MasterSend time of sync packet
T2SlaveReceive time of sync packet
T3SlaveSend time of reply
T4MasterReceive time of reply

T2 and T3 are in slave time. T1 and T4 are in master time. Combining them cancels out the one-way delay (assuming symmetry) and isolates the offset. The slave then adjusts its clock by the computed offset.

Sources of Error

The paper breaks message delay into four components: send time (OS overhead), access time (MAC layer wait), propagation time (speed of light over distance), and receive time (NIC processing). Of these, send time is the biggest source of nondeterminism on a platform like this. Timestamping as close to the radio layer as possible reduces it. On the ESP8266 that means stamping inside the UDP send callback rather than in application code.

Engineering Notes

Technical Reference

Sender-Receiver vs. Receiver-Receiver

RBS (Reference Broadcast Synchronization) eliminates sender uncertainty by synchronizing two receivers to a third-party pulse instead of to the sender directly. The paper argues this is more accurate because the sender's nondeterminism is the largest error source. But RBS needs more messages: 4 sent and 3 received per sync pair vs. 2 and 2 for two-way exchange. On three nodes with limited Wi-Fi bandwidth, the simpler sender-receiver approach is a reasonable starting point.

Software Clock Correction

The paper recommends against modifying the raw hardware clock and instead maintaining a conversion table: each node keeps the estimated offset and drift relative to the master and applies the transform when a synchronized timestamp is needed. This avoids discontinuities from hard clock resets.

millis() Resolution

The Arduino millis() function returns milliseconds. For sync targets in the single-digit millisecond range, that ceiling matters. The ESP8266 also has micros() for microsecond resolution, which is worth using for T1 and T4 on the master side to reduce quantization error in the offset calculation.

UDP vs. TCP

UDP is the right choice here. TCP adds retransmission and connection overhead that makes message delay harder to characterize. The sync packets are small and losing one just means skipping a round, which is acceptable.

millis() Overflow

millis() wraps around at about 49 days on a 32-bit counter. For short experiments this doesn't matter, but the timestamp arithmetic needs to handle wrap-around correctly if the boards run for extended periods.

Why Traditional Methods Don't Work

NTP is designed for internet-scale networks with stable hardware. Sensor nodes have tight energy budgets, high node density, and potentially unreliable links. GPS is too expensive and doesn't work indoors. The paper's key insight is that algorithms for sensor networks need to be lightweight and tolerant of delay uncertainty.

Tiny-Sync / Mini-Sync

Each two-way exchange produces a data point (T0, Tb, Tr) that constrains the possible drift and offset values. Mini-Sync finds optimal bounds from all data points collected. More exchanges tighten the bounds. This is essentially bounded-error parameter estimation, which is a clean way to think about the problem when message delays are unknown but bounded.

The paper is worth reading in full. The breakdown of delay sources (send time, access time, propagation time, receive time) is a useful mental model for any distributed timing problem.
